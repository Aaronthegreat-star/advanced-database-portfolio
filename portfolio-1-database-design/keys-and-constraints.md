# Keys and Constraints: lenddesk_users

This document explains the keys and constraints in `schema.sql` and why each
was chosen.

## Primary keys
| Table | Primary key | Reason |
|---|---|---|
| organizations, roles, permissions, users | `id` CHAR(36), UUID | Unguessable, can be generated by the application before insert, and other microservices can store a `user_id` without depending on this database's sequence |
| role_permissions | (role_id, permission_id) | Composite key: each pairing can exist only once, so no surrogate id is needed |
| user_activity_logs | `id` BIGINT AUTO_INCREMENT | Very large append-only table; ordered inserts avoid the index fragmentation random UUIDs cause |

**Trade-off:** a UUID takes 36 bytes against 8 for a BIGINT and inserts in
random order into the InnoDB clustered index. This is accepted for the business
tables because they are small and read-heavy. The effect is measured in
Portfolio 2.

## Foreign keys
| Child column | Parent | ON DELETE | Reason |
|---|---|---|---|
| roles.organization_id | organizations.id | CASCADE | Roles have no meaning without their organisation |
| users.organization_id | organizations.id | RESTRICT (default) | An organisation that still has users must not be deleted by accident |
| users.role_id | roles.id | SET NULL | Deleting a role leaves the user without a role; the user is kept |
| role_permissions.role_id | roles.id | CASCADE | Assignments follow the role |
| role_permissions.permission_id | permissions.id | CASCADE | Assignments follow the permission |
| user_activity_logs.user_id | users.id | RESTRICT (default) | Audit history must not disappear; users are soft-deleted instead |

No foreign key points outside this database. Other services (loans,
repayments) are separate microservices and reference users by `user_id` only.

## Unique constraints
- `organizations.slug`: one URL-safe identifier per tenant
- `permissions.name`: no duplicate permission names
- `(roles.organization_id, roles.name)`: role names are unique within an organisation
- `(users.organization_id, users.email)`: an email is unique within an organisation, not globally, because tenants are independent

## NOT NULL, defaults and CHECK
- Names, email and `password_hash` are NOT NULL.
- `is_active` defaults to 1 and `failed_logins` defaults to 0.
- `CHECK (failed_logins >= 0)` prevents an invalid counter.
- `users.role_id` and `users.deleted_at` are nullable on purpose: a user may have no role, and `deleted_at` is set only when the user is soft-deleted.

## Soft delete
Users are marked with `deleted_at` and `is_active` instead of being removed, so
`user_activity_logs` keeps its audit history and the foreign key never needs to
cascade.
