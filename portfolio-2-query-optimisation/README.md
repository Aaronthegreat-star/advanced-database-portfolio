# Portfolio 2: Query Processing and Optimisation

**Case study:** LendDesk, a multi-tenant SaaS loan management platform (database `lenddesk_users`, designed in Portfolio 1).
**Question:** how much does a composite index speed up a reporting query on the largest table, `user_activity_logs`?
**Answer in one line:** the index cut the query from about 24.9 s to 0.5 s on 2,000,000 rows, and the plan changed from a full scan with a sort to a narrow index range scan.

## 2. Test environment

- MySQL 8.0.46 in a Docker container (`mysql:8.0`), queried with HeidiSQL.
- Schema created from the Portfolio 1 `schema.sql` (database `lenddesk_users`).
- Before the optimisation, `user_activity_logs` had only its primary key and the automatic foreign-key index `fk_logs_user (user_id)`.

## 3. How the database was populated

No real customer data was used. The tables were filled with **synthetic test data generated by `seed-data.py`** (Python with `pymysql`), run with a fixed random seed (`8103`) so the data can be reproduced:

```bash

```

Activity-log details: ten actions (`LOGIN`, `LOGOUT`, `VIEW_LOAN`, `CREATE_LOAN`, `APPROVE_LOAN`, `RECORD_REPAYMENT`, `VIEW_CUSTOMER`, `UPDATE_CUSTOMER`, `EXPORT_REPORT`, `PASSWORD_RESET`) with realistic weights and HTTP-style status codes (200, 201, 401, 403, 404, 422, 429, 500). Activity is skewed so a few users are much busier than the rest, as in real systems. Password hashes are a fixed dummy value, not real credentials. Resulting size: `user_activity_logs` 340.7 MiB, `users` 38.7 MiB.

## 4. SQL query tested

Business question: which 10 users were most active in the last 30 days (for example, for a platform usage dashboard)?

```sql
SET @ref = (SELECT MAX(created_at) FROM user_activity_logs);

SELECT user_id, COUNT(*) AS actions
FROM user_activity_logs
WHERE created_at >= @ref - INTERVAL 30 DAY
GROUP BY user_id
ORDER BY actions DESC
LIMIT 10;
```

`@ref` is the newest log time, so the 30-day window is repeatable.

**Query result:** the same 10 rows came back before and after indexing (top user 809 actions, then 286, 233, 199, 180, 160, 127, 117, 115, 114). The index changes speed, not the answer.

## 5. Optimisation

```sql
CREATE INDEX idx_logs_created_user ON user_activity_logs (created_at, user_id);
ANALYZE TABLE user_activity_logs;
```

`created_at` comes first because the query filters on a date range. `user_id` is included so MySQL can answer from the index alone, without reading table rows (a covering index). Building the index took 24.4 s and adds extra disk space.

## 7. Results

| | Before indexing | After indexing |
| --- | --- | --- |
| Time | 24.922 s | 0.500 s |
| Access type | `index`: full scan of `fk_logs_user` | `range`: only the last 30 days of `idx_logs_created_user` |
| Rows examined (estimate) | 1,989,368 | 319,670 |
| Extra | `Using where; Using temporary; Using filesort` | `Using where; Using index` (covering) |

**Why it is faster:** before the index, MySQL read about 2,000,000 entries to find 30 days of activity. After it, MySQL jumps to the start of the date range and reads about 16% of the rows, all from the index.

**Limits of this test:** the "before" time comes from HeidiSQL's log for three statements (`USE`, `SET @ref` and the `SELECT`), and `SET @ref` also scans the table to find `MAX(created_at)`, so the before figure slightly overstates the query alone. Only one query was measured, on one machine, so exact times will differ elsewhere. The conclusion (a full scan became a narrow range scan) does not depend on those details.

**Trade-off:** the index costs 24.4 s to build, extra disk space, and slightly slower inserts into `user_activity_logs`. For an activity log that dashboards read far more than it is written, this is a good trade.
